# Discovery workflow

1. Resolve the project root from the user's prompt or current working directory and load `.job-search.local.json`. When `reliability.require_preflight` is true, run `node scripts/preflight.mjs` first. Stop on failed checks; surface warnings and inspect pending recovery markers before any workbook write.
2. Run `node scripts/export_search_config.mjs`, `node scripts/export_eligibility_evidence.mjs`, and `node scripts/build_search_queries.mjs`. Treat the outputs as authoritative. The query builder uses the configured timezone to decide whether a weekly watchlist is due. Supply only fresh, in-scope registry evidence to agents and keep all registry conclusions subordinate to current canonical-vacancy evidence. Read the configured candidate profile, configured search-terms file, `profile/candidate-packet-schema.md`, prior leads, and configured `state_directory/last-run.json` when present.
   - When `gmail_job_alerts.enabled` is false, do not access Gmail or read a private batch. When it is true and the user supplies a private version-1 batch, run `npm run ingest-alerts -- --input <private-batch>` without `--apply` first. Report the sanitized preview and classifications. Use `--apply` only for an explicit persistent import; it atomically stores the same sanitized proposal in private state and never touches the workbook.
   - For each proposed alert candidate, open only the public vacancy URL, verify the current canonical source and listing status, collect the same job evidence as a normal finder, and route it through the blind judge. Retain the `gmail_alert_finder` query ID and sanitized provenance. Never pass an unverified proposal directly to `update_tracker.mjs` and never copy email bodies, subjects, senders, message IDs, or raw tracking URLs into the run.
3. Create a unique run ID and record timestamps in the configured timezone.
4. Use the exported role and agent query budgets. Run both finders in parallel.
5. Give each finder the complete packet schema, candidate profile with stable evidence IDs, exported configuration, active eligibility-evidence snapshot, and only that finder's exact query-plan entries, caps, and read-only rule. Require each plan entry to be attempted once, `query_count` to equal the number attempted, and `query_attempts` to contain one `Completed|Failed` record for each supplied query ID, role family, source, and lane. A failed attempt carries a concise error and makes the combined run `Partial`. If a named project agent is unavailable, use a generic read-only subagent with the same prompt and record the fallback.
6. For `linkedin_public` plan entries, use the exact title-focused Boolean string and supplied freshness/location/workplace filters. Do not add skills, exclusions, sponsorship, relocation, or other narrowing terms to the discovery query. After finding a vacancy, apply `post_discovery_screening` together with the complete eligibility and scoring policy. Read only public job-detail pages without signing in. Record the query ID and LinkedIn job ID; convert 404/410 pages, unrelated redirects, and no-longer-accepting notices to scan events. Prefer employer or public ATS pages, resolving them from LinkedIn when available. Use the plan's `canonical_source_adapters` registry to identify supported public ATS sources and record `canonical_source_adapter`; record `canonical_source_status` only from live page evidence. Never use private APIs, authenticated sessions, access-control bypasses, or submission endpoints, and never infer activity or eligibility from a URL. Canonicalize URLs, deduplicate by employer job ID, canonical URL, then normalized company/title/location. Preserve every other examination as a scan event.
7. For `company_watchlist` entries, read the public directory, filter it by the supplied market terms, and inspect no more than `max_companies_per_run`. The directory row is only a seed: open the linked public careers page, find a role matching the query's titles, and resolve an active canonical vacancy before returning a packet. Do not create a scan event merely because a company was listed or had no matching vacancy. Put the configured `interview_process_signal` in a verified vacancy packet without adding score points, and note that the current process still needs confirmation.
8. Suppress expired or inaccessible listings and explicit residency, unsupported-country, or work-authorization blockers. Retain unclear sponsorship for review with reduced location points.
9. Select at most the configured judge maximum from candidates meeting the judge threshold. Blind the judge by removing finder eligibility, finder eligibility registry IDs, finder listing status, finder scores, total, recommendation, strengths, gaps, best resume, and any watchlist `interview_process_signal`. Preserve the signal and finder registry IDs separately and restore them only after judging.
10. Give `job_judge` only canonical job evidence, source links, active eligibility-evidence snapshot, candidate evidence, rubric, and exported configuration. Require the judge envelope, independent judge registry IDs, and structured listing status. Convert per-candidate failures or omissions into failed-judge records.
11. Convert finder/judge eligibility disagreements or unsupported evidence to `Needs Human Review`. A judge-verified `Expired` or `Inaccessible` listing remains `Ineligible`. Never infer listing status from rationale keywords.
12. Build the run payload from `schemas.md`, combining finder `query_attempts` in generated-plan order and stable unique finder/judge registry IDs as `eligibility_evidence_ids`. An alert-backed run may include optional `agents.gmail_alert_finder` status and its attributed query attempt. Include `replay_context` with the exact generated query entries, screening filters, exported thresholds/caps, and stable profile/registry snapshot identifiers. Every candidate and scan event must retain the matching `discovery_query_id`; every retained candidate must carry one allowed `best_resume`. Resolve `tracker_path`, `state_directory`, and the optional existing registry from local configuration and call `scripts/update_tracker.mjs`, adding `--eligibility-registry` when present. This is the only discovery write path and it applies the established table-body formatting to every appended Leads, Scan Log, Run Log, Query Metrics, and Eligibility Review row. The updater appends a watchlist interview-process signal to Notes and explicitly marks it unscored. It also upserts strong unresolved cases into `Eligibility Review`, preserves user-controlled Status and Resolution fields, refreshes the derived Action Dashboard, and privately archives the exact run input and result with a deterministic replay hash.
13. On the weekly monitoring run, give `change_monitor` only `Shortlisted` and `Moved to Applications` leads, their exact canonical URLs and current tracker values, plus the active registry snapshot. Require one source-backed check per lead using the monitoring schema, then call `scripts/monitor_leads.mjs` with the configured workbook, state directory, and registry path when present. The legacy `scripts/recheck_expiry.mjs` remains accepted for expiry-only packets.
14. Publish only updater-returned alerts, ordered by judge score and capped by Search Config. If notification preferences are enabled, run `npm run notify` as a read-only preview over the updater result and report the exact approval ID; never apply without that exact approval. Optional connector capability discovery is a network-free private export import: preview first and require exact `NCAP-…` approval only for its sanitized catalog, which never authorizes delivery or mutates a profile. Catalog-to-binding drift, chronological catalog-history inspection, and exact catalog-to-profile planning are read-only and never upgrade uncertainty or grant send permission; an authoring plan writes no profile and issues no approval. A live connector is a later, separate action over an approved outbox request and additionally requires an approved sanitized binding plus explicit `--send` with the same exact request approval. Version-2 connector profiles may render bounded Slack Block Kit JSON in memory, but their target and rendered body remain private and absent from preview/recovery output. Provider-status reconciliation is another separate action: import its sanitized binding, preview without credentials or network, and use a single explicit `--probe` only after exact `NSTAT-…` approval. Use `npm run notify-health` only as a read-only operational view over outbox requests, sanitized receipts, sanitized provider observations, and redacted recovery markers; it never authorizes a probe, sends, or retries. If no alert qualifies, include the updater's compact diagnostics summary and warnings so `no priority leads`, `no discoveries`, and `thin coverage` remain distinct outcomes.

An empty finder result is successful. A fallback is recorded explicitly. One finder failure produces a partial run. A workbook write failure preserves the workbook and records a pending payload in the configured state directory.
