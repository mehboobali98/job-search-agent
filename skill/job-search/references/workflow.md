# Discovery workflow

1. Resolve the project root from the user's prompt or current working directory and load `.job-search.local.json`.
2. Run `node scripts/export_search_config.mjs` and `node scripts/build_search_queries.mjs`. Treat both outputs as authoritative. The query builder uses the configured timezone to decide whether a weekly watchlist is due. Read the configured candidate profile, configured search-terms file, `profile/candidate-packet-schema.md`, prior leads, and configured `state_directory/last-run.json` when present.
3. Create a unique run ID and record timestamps in the configured timezone.
4. Use the exported role and agent query budgets. Run both finders in parallel.
5. Give each finder the complete packet schema, candidate profile with stable evidence IDs, exported configuration, and only that finder's exact query-plan entries, caps, and read-only rule. Require each plan entry to be attempted once, `query_count` to equal the number attempted, and `query_attempts` to contain one `Completed|Failed` record for each supplied query ID, source, and lane. A failed attempt carries a concise error and makes the combined run `Partial`. If a named project agent is unavailable, use a generic read-only subagent with the same prompt and record the fallback.
6. For `linkedin_public` plan entries, use the exact title-focused Boolean string and supplied freshness/location/workplace filters. Do not add skills, exclusions, sponsorship, relocation, or other narrowing terms to the discovery query. After finding a vacancy, apply `post_discovery_screening` together with the complete eligibility and scoring policy. Read only public job-detail pages without signing in. Record the query ID and LinkedIn job ID; convert 404/410 pages, unrelated redirects, and no-longer-accepting notices to scan events. Prefer employer or public ATS pages, resolving them from LinkedIn when available. Canonicalize URLs, deduplicate by employer job ID, canonical URL, then normalized company/title/location. Preserve every other examination as a scan event.
7. For `company_watchlist` entries, read the public directory, filter it by the supplied market terms, and inspect no more than `max_companies_per_run`. The directory row is only a seed: open the linked public careers page, find a role matching the query's titles, and resolve an active canonical vacancy before returning a packet. Do not create a scan event merely because a company was listed or had no matching vacancy. Put the configured `interview_process_signal` in a verified vacancy packet without adding score points, and note that the current process still needs confirmation.
8. Suppress expired or inaccessible listings and explicit residency, unsupported-country, or work-authorization blockers. Retain unclear sponsorship for review with reduced location points.
9. Select at most the configured judge maximum from candidates meeting the judge threshold. Blind the judge by removing finder eligibility, finder listing status, finder scores, total, recommendation, strengths, gaps, best resume, and any watchlist `interview_process_signal`. Preserve the signal separately and restore it unchanged only after judging.
10. Give `job_judge` only canonical job evidence, source links, candidate evidence, rubric, and exported configuration. Require the judge envelope and structured listing status. Convert per-candidate failures or omissions into failed-judge records.
11. Convert finder/judge eligibility disagreements or unsupported evidence to `Needs Human Review`. A judge-verified `Expired` or `Inaccessible` listing remains `Ineligible`. Never infer listing status from rationale keywords.
12. Build the run payload from `schemas.md`, combining finder `query_attempts` in generated-plan order. Every candidate and scan event must retain the matching `discovery_query_id`; every retained candidate must carry one allowed `best_resume`. Resolve `tracker_path` and `state_directory` from local configuration and call `scripts/update_tracker.mjs`. This is the only discovery write path and it applies the established table-body formatting to every appended Leads, Scan Log, Run Log, and Query Metrics row. The updater appends a watchlist interview-process signal to Notes and explicitly marks it unscored.
13. On Fridays, recheck canonical URLs for `Shortlisted` and `Moved to Applications` leads, then call `scripts/recheck_expiry.mjs` with source-backed evidence.
14. Publish only updater-returned alerts, ordered by judge score and capped by Search Config. If no alert qualifies, include the updater's compact diagnostics summary and warnings so `no priority leads`, `no discoveries`, and `thin coverage` remain distinct outcomes.

An empty finder result is successful. A fallback is recorded explicitly. One finder failure produces a partial run. A workbook write failure preserves the workbook and records a pending payload in the configured state directory.
